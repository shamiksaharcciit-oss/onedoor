stay that way. **Do not backfill releases onto older tags** — a retroactive release carries

## 7. What I will verify afterwards, and why it is worth the step

The same pattern that verified `0.4.0`, `0.4.1` and `0.5.0`, and it is **not** a repeat of
§2 — §2 checks what we built, this checks **what they hold**:

- **`sha256` from PyPI's own index API**, not from the upload transcript. An upload
  transcript is the sender's account of what it sent; the index API is the receiver's
  record of what it has. Both digests must equal the two above.
- **Both artifacts re-downloaded** from PyPI *and* from the GitHub release, and compared
  byte-for-byte against `dist/`.
- **The annotated tag dereferenced.** `gh api .../git/ref/tags/v0.6.0` returns the **tag
  object's** SHA, not the commit — on `0.5.0` that nearly produced a false mismatch report.
  The tag object is dereferenced to its commit and compared against `git rev-list -n1`.
- **A fresh venv installing `onedoor==0.6.0` from PyPI**, exercising the Studio spine end
  to end.

compared.*
