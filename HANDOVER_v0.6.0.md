## 0. Read this first — do not rebuild

**The digests in §3 are of the exact files sitting in `dist/` right now. Upload those
files. Do not run `python -m build` again before uploading.**

Measured rather than assumed: **this build is not byte-reproducible.** Two builds from the
*same* source tree produce different bytes — the wheel keeps its size and changes its
hash, and the sdist changes size as well, because zip and gzip both record timestamps.

That is not a defect and there is nothing to fix here; it is a property of the tooling, and
the same lesson the demo ledger already taught (*the database FILE is not byte-reproducible
and cannot be; the pinned artifact is the chain head*). It only matters because it decides
what this handover can promise: **these digests identify the files to publish, not a
recipe that would recreate them.** If `dist/` is ever rebuilt, tell me and I will reissue
the digests rather than let a stale pair be checked against a fresh artifact.

## 7. What I will verify afterwards, and why it is not a repeat of §2

§2 checks **what we built**. The post-publish pass checks **what they hold** — the same
pattern that verified `0.4.0`, `0.4.1` and `0.5.0`:

- **`sha256` from PyPI's own index API**, not from the upload transcript. An upload
  transcript is the sender's account of what it sent; the index API is the receiver's
  record of what it has. Both must equal §3.
- **Both artifacts re-downloaded** from PyPI *and* from the GitHub release, compared
  byte-for-byte against `dist/`.
- **The annotated tag dereferenced.** `gh api .../git/ref/tags/v0.6.0` returns the **tag
  object's** SHA, not the commit — on `0.5.0` that nearly produced a false mismatch report.
  It is dereferenced to its commit and compared against `git rev-list -n1 v0.6.0`.
  *An identifier is answered at a layer; name the layer or you do not know what you
  compared.*
- **A fresh venv installing `onedoor==0.6.0` from PyPI**, exercising the Studio spine end
  to end.
