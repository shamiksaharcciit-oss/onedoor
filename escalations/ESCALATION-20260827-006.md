# Delivery → Core · Escalation 006 — F-B: decimal strings in `params`

**From:** onedoor delivery · **To:** core · **Date:** 2026-08-27
**Re:** F-B from the `0.6.0` operator validation. **Read, with a proposal. Not fixed.**
**Status:** needs a ruling — the change is **wire-observable**, which makes it core's.

---

## 1. The report, and what measuring it found underneath

Reported: `params` numeric bounds refuse decimal strings (`"40.00"` → `bounds` / *must be
numeric*) while `cost_eur` accepts them — two number conventions in one request body.

That is true, and the mechanism is plain: `cost_eur` is a Pydantic model field, so
`"40.00"` is coerced to `Decimal`; `params` is `dict[str, JsonValue]` with no coercion,
and `bounds.py:42` accepts only `int | float | Decimal`.

**But the sharper defect is inside the engine, and it needs no spec to be wrong.**
`caps.resolve_cost` (`caps.py:139`) **explicitly accepts `str`** and converts with
`Decimal(str(raw))`. So one `params` value is **numeric enough to spend budget against and
not numeric enough to be range-checked.**

Measured on the shipped code, same request both times:

```
params {"amount_eur": "40.00"}

A. policy declares cost_param, NO numeric bound
   resolve_cost sees: Decimal('40.00')      -> PERMITTED, 40 EUR charged to the cap

B. SAME policy plus numeric bound max=2000  (a TIGHTER policy)
   resolve_cost sees: Decimal('40.00')      -> denied / bounds
```

**Adding a `max` changes which wire types the endpoint accepts.** Tightening a policy
changes its parsing surface. Nobody designed that; it fell out of two places answering
*"is this a number?"* independently.

**Direction of failure:** B fails **closed**, so there is no open door here. A is the
uncomfortable one — the engine *already* treats decimal strings as money in the cap path,
which means **the bounds path is the outlier, not the caps path.**

## 2. The read core asked for: impl, spec, or both

**Both, and they interact — but they are separable and only one is delivery's.**

**The implementation is internally inconsistent, independently of the spec.** Two
functions in one engine give different answers about one value from one dict. Whatever
AADP-01 says, those two must agree; a spec ruling cannot make them consistent, it can only
choose which way. **This half is a defect on its own terms.**

**The spec under-specifies `params` typing.** What `CONFORMANCE.md` records as *"decimal
string, never float"* (§ line 756, and `models.py`'s `Budget` docstring) is about the
**budget object** — a structure onedoor *generates* and hashes, where E8's *wire = storage
= preimage* has to hold. `params` are the other discipline entirely: **received data**,
frozen verbatim at ingress, never re-serialised (E10/R004). Nothing in the recorded surface
says what type a caller must use for a numeric parameter. So an integrator who reads
AADP-01, sees money as decimal strings, and sends `"40.00"` is behaving reasonably and gets
a denial.

**The interaction is what made it land on an operator rather than in review.** Because the
spec is silent, the two halves drifted; because they drifted, the symptom presents as the
absurd coupling in §1 rather than as a plain type error.

## 3. Proposal

**Align bounds to caps — accept a strict decimal string in `params` — and make the two
paths share one function so they cannot diverge again.**

The last clause is the actual fix. The defect is not "bounds is too strict"; it is that
**two implementations of one fact eventually disagree**, which this programme has ruled on
repeatedly. One `numeric_value(raw) -> Decimal | None`, called by `bounds` and by
`resolve_cost`, with a test asserting they cannot answer differently.

Three constraints on the accepting side:

1. **Strict.** The same construction `resolve_cost` already performs — `Decimal(str(raw))`
   with the finiteness and non-negative checks — and nothing looser. No whitespace
   tolerance, no exponent forms smuggled past, and `NaN`/`Infinity` stay **malformed**
   (E10), not "not numeric".
2. **Interpretation for evaluation only.** The frozen `params_json` is untouched, byte for
   byte. This is not normalising received data; it is reading it. `resolve_cost` has always
   done exactly this.
3. **`bool` stays excluded** in both paths, as both already do.

**Why not the other direction** — making `resolve_cost` refuse strings: it would turn
currently-permitted actions into `cost_unknown` denials, it would make onedoor refuse
AADP-01's own wire form for money, and it is squarely breaking. Delivery does not
recommend it.

## 4. Why this is not in `0.6.1`

**It changes a verdict from `denied` to `permitted` for an input the engine accepts
today.** That is wire-observable behaviour, and delivery does not change wire-observable
behaviour on its own authority — the standing boundary, and the one that has found five
real defects by being obeyed.

It is additive in the compatibility sense (nothing currently permitted becomes denied) but
it is a **widening**, and a widening in a guardrail deserves a ruling rather than a
maintainer's judgement. `0.6.1` carries F-A, F-C, F-D and F-E only.

**One thing delivery has *not* done and will not without a ruling:** silently make the
`params` path stricter to match bounds, which would be the "consistent" fix that breaks
working integrations.

## 5. Question

1. **Which way do the two paths agree** — bounds accepts decimal strings (delivery's
   proposal), or something else?
2. **Does AADP-01 type `params` at all**, and if not, should it? Delivery reads the
   decimal-string convention as belonging to *generated* structures, and `params` as
   deliberately caller-shaped received data — but that reading is exactly what a spec
   should state rather than leave to be inferred.
3. **Is the widening allowed before the freeze lifts**, or does it wait with `ND-053`?
   Delivery's own lean is that it waits: it is not a launch blocker, the failing direction
   is closed, and a verdict-changing fix rushed into launch week is the shape the freeze
   exists to prevent.

Interim, and shipping in `0.6.1`: the README's quickstart states that `params` numbers are
JSON numbers, and *Known limitations* names the asymmetry — so an integrator meets it in
documentation rather than in a denial.
