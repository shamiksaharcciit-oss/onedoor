## E6 · The `protocol`-scoped reading rule has no column to read

**Severity: blocks the `-02` text of E1.4, not the code.** Delivery can build the
column; only the fallback rule is core's.

E1.4 rules that a conformant reader interprets each row's `reason_code` "scoped to
the `protocol` version recorded on that row." Verified at `3dfe3cd`:

```
grep -rn "protocol" onedoor/service/app.py onedoor/guardrail/models.py   # no matches
```

The only `protocol` string in the entire package is MCP's own `protocolVersion` in
`mcp/demo_server.py:75` — unrelated.

**`actions_audit` has no `protocol` column.** Its columns are `id`, `request_id`,
`kind`, `parent_id`, `action_type`, `source`, `params_json`, `decision`,
`reason_code`, `nominal_tier`, `effective_tier`, `detail`, `connector_ok`,
`error`, `payload_json`, `approval_id`, `undo_until`, `undo_of`, `created_at`.
No AADP protocol version is stamped on the wire or in the evidence store anywhere.

So the rule as written is unimplementable in both directions:

- **Forward** — fixable. Delivery adds a `protocol` column in the `0.4.0`
  migration and stamps every new row. No ruling needed; this is now on `ND-002`.
- **Backward** — **not fixable, ever.** Every row written before `0.4.0` has no
  protocol stamp, and `actions_audit_no_update` forbids adding one. A reader
  handed a mixed archive finds rows carrying `cap_eur_day` with a NULL scope.

**Ruling requested.** The `-02` text needs an explicit fallback: *absence of a
recorded `protocol` on an evidence row MUST be interpreted as `aadp/0.1`* (or
whatever string designates the pre-`0.2` vocabulary). Without that sentence, E1.4
moves re-derivability from "undocumented reader convention" to "documented rule
that silently doesn't apply to the majority of existing rows" — which is the same
defect one level down.

Suggested wording, if useful:

> An evidence row that records no `protocol` value MUST be interpreted under the
> `aadp/0.1` reason-code vocabulary. PDPs advertising `aadp/0.2` or later MUST
> record `protocol` on every evidence row they append.

## E7 · `cap_value` collapses two codes into one, and the distinguishing detail is response-only

**Severity: an audit-granularity regression shipped by `0.4.0` unless resolved.**

E1.1 maps `cap_eur_day` **and** `cap_eur_month` → the single `cap_value`, with the
window moving into the `budget` object. E1.2 scopes that object as a field on the
**Decide Response**.

The draft is silent on whether `budget` is *persisted to the evidence row*. If it
is not, `0.4.0` makes the audit strictly less informative than `0.3.5`:

| | Day-cap breach | Month-cap breach |
|---|---|---|
| `0.3.5` audit row | `reason_code = cap_eur_day` | `reason_code = cap_eur_month` |
| `0.4.0`, budget not persisted | `reason_code = cap_value` | `reason_code = cap_value` |

The two become indistinguishable in the evidence store. Today the window survives
only in `detail` as prose — `caps.py:141` writes `f"€/day cap {caps.eur_day}
reached{label}"` — which is not machine-readable and is exactly the free-text
representation `ND-003` exists to replace.

This bears directly on §evidence: a verdict whose evidence row cannot say *which
budget window* was exhausted is not fully re-derivable from that row.

**Delivery's position:** the `budget` object MUST be persisted on the evidence row
(`budget_json`, canonically rendered), not merely returned. Delivery will build it
that way — evidence content is arguably delivery's call — but flags it because it
reads as a §evidence requirement that the `-02` text should state rather than
leave to an implementer's judgement. **Confirm or correct.**

*Non-blocking companion:* E1.2 makes `budget` present **iff** the verdict is `deny`
with reason ∈ {`cap_value`, `cap_rate`}. That means a *permit* carries no budget
telemetry, so the GUI's budget gauges (`ND-018`, roadmap §4.2) need a separate read
path rather than observing the decision stream. Fine for conformance, and delivery
will build the side-channel — noting only in case core would rather allow an
OPTIONAL `budget` on permits later.

## E8 · Decimal canonicalisation has no scale rule — and today's values would hash inconsistently

**Severity: blocks the E3 canonicalisation freeze. This one must be settled before
`ND-001` writes its first chained row.**

E3 grants the freeze and enumerates the rules: column order; JSON keys sorted;
NFC; decimal rendering per §messages; RFC3339 UTC datetimes. E1.2 illustrates with
`"limit": "250.00"`, `"remaining": "0.00"`.

**§messages says "decimal string, never float." It does not pin the *scale*.** That
is sufficient for a wire format and insufficient for a hash preimage.

Verified in the source: caps are parsed into Python `Decimal` and carry whatever
scale the policy author wrote (`guardrail/caps.py:139–149`). So:

- `eur_day: 250` in `policies.yaml` → `Decimal("250")` → renders `"250"`
- `eur_day: 250.00` → `Decimal("250.00")` → renders `"250.00"`

Same policy, same limit, **different canonical bytes, different `row_hash`,
different content-addressed digest.** Two operators with semantically identical
policies produce non-comparable archives, and a verifier re-deriving from a policy
snapshot whose YAML was reformatted gets a mismatch on an unchanged rule.

It also isn't obvious what the right answer is, which is why delivery won't pick
one unilaterally:

- **Scale from the unit's minor units** (EUR → 2dp) is natural for `"value"`, but
  `"rate"` budgets have unit `"calls"` with no minor units — is `10` rendered
  `"10"` or `"10.00"`?
- **Normalise to shortest exact form** (strip trailing zeros → `"250"`, `"0"`)
  is unit-agnostic and idempotent, but contradicts your `"250.00"` / `"0.00"`
  examples.
- **Preserve authored scale** is what the code does today and is exactly the
  non-determinism above.

**Ruling requested:** the exact decimal-rendering rule for the canonical preimage —
covering scale, trailing zeros, negative zero, and whether the rule differs between
a `"value"` dimension and a `"rate"` dimension. Delivery suggests **normalise to
shortest exact form, uniformly, for the hash preimage**, and treat the wire
rendering in E1.2 as presentational — but this is §messages territory and yours.

Whichever way it goes, it should be frozen in the same `-02` edit as the rest of
the canonicalisation rules (your change-list item 7), because it is part of the
same preimage.

## E9 · A3 was never put to core — delivery's omission, not core's

Recorded rather than quietly fixed. **Escalation 001 did not ask anything about
A3** (downstream idempotency-key propagation), so Response 001 correctly says
nothing about it — but `ND-008` carries open core questions that have simply never
been asked, and it sits in the `0.5.0` release.

The questions, now formally raised:

1. Does the draft specify the **derivation function** for a permit-derived
   idempotency key, and the **header/field name** it travels under
   (`Idempotency-Key`, or otherwise)? If it does not, delivery proposes deriving it
   deterministically from the permit and documenting the mapping per adapter.
2. **What is the conformant behaviour when the target system has no idempotency
   support?** Three defensible readings: a denial, an obligation the PEP must
   refuse to discharge, or a documented caveat. These differ materially.

The second matters more than it looks. Connectors are pluggable
(`connectors/mock.py`), so the engine can only ever *offer* the key — whether the
target honours it is the adapter's contract. Without a ruling, onedoor risks
documenting "exactly-once effect" while delivering "exactly-once decision plus a
key we hope someone uses." That is precisely the overclaiming the brief forbids.

**Not urgent** — `ND-008` is two releases out. Flagged now so it is not discovered
at implementation time.
