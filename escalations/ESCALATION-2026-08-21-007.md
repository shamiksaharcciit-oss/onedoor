**From:** onedoor delivery · **To:** core · **Date:** 2026-08-21

**Assessed at:** shipped `0.3.6` = `6a95a69`, the published tag.

## 1. S3 — confined to stored text. Nothing compares it. W3 can close it quietly.

The question was whether `str(Decimal)` storing equal values as different text can
reach a decision. **It cannot.** Four independent lines, structural and empirical:

- **Money is in no key or index.** `cap_counters`'s PRIMARY KEY is
  `(action_type, window_kind, window_key)`; `eur_total` is not part of it, so
  differing spellings cannot split a counter row.
- **The text is never compared in SQL.** Every occurrence of `eur_total` is either
  `SELECT`ed and immediately wrapped in `Decimal(...)`, or written via `str(...)`.
  No `WHERE`, `ORDER BY`, `GROUP BY`, or comparison touches it.
- **The round trip is value-preserving.** `Decimal(str(d)) == d` held on **4000/4000**
  generated values spanning plain, scaled, exponent, sub-unit and large-magnitude
  forms. Over **40,000** generated comparisons, the round trip flipped **zero**
  outcomes. Accumulating 500 mixed-spelling values through text equalled the exact
  sum.
- **End to end on the real engine**: four spellings of €2.50 against a €10.00 daily
  cap stored as `2.50` → `5.00` → `7.500` → `10.000` — visibly inconsistent text —
  and the next €0.01 denied at exactly the right boundary.

So the defect is real but inert: it makes the audit's *text* untidy and would break a
future digest over that column, which is precisely why W3 fixes it. **No disclosure
warranted for S3.**

## 2. S2 — this one reaches enforcement, in shipped `0.3.6`

The survey listed S2 as "bounds are float while `cost_eur` is Decimal". Assessing it
alongside S3 shows it is the one with a decision path, so it is reported here rather
than waiting to be asked.

**The mechanism.** `json.loads` runs with no `parse_float`, so a numeric parameter
becomes an IEEE double *before any check sees it*. `bounds.py` then compares that
double against a bound that is also a double. A wire amount carrying more precision
than a double holds is rounded onto the bound and admitted.

**Demonstrated**, not reasoned:

```
policy max            500.10
amount on the wire    500.1000000000000000001     (genuinely over the cap)
after json.loads      500.1                        (a float)
bounds verdict        ALLOWED
```

**Magnitude is derived, not guessed.** The admitted excess is about half an ulp of the
bound, so it scales with the bound's magnitude. All four demonstrated over-cap and
admitted:

| bound | max admitted excess |
|---|---|
| `500.10` | ~5e-14 |
| `1000000.00` | ~5e-11 |
| `1000000000000.00` | ~0.00005 |
| `100000000000000000` | **~10** |

**Both directions.** The symmetric case — a compliant value rounded *up* and falsely
denied — also exists. That one fails closed, so it is a correctness bug rather than a
safety one.

**It reaches the cap amount too, not only the bounds gate.** `resolve_cost` does
`Decimal(str(raw))`; for a float `raw` that re-rounds to the shortest decimal, so the
counter is charged the *intended* amount rather than the float's exact value. The
precision was already gone at ingress, so the amount charged can differ from the
amount requested by the same ~half-ulp.

**Two mitigations, stated so the disclosure is not overstated:**

1. **Only JSON *numbers* are affected.** `resolve_cost` accepts `str`, and a money
   amount sent as a JSON string (`"500.10"`) is exact end to end. Callers already
   sending money as strings are unaffected.
2. **For realistic money caps the excess is far below one cent** — 5e-14 at €500.10.
   It becomes material only for large-magnitude bounds, which are plausible for
   non-money numeric bounds (byte counts, token counts) rather than for euros.

**Delivery's read:** a genuine enforcement mis-decision, of negligible economic
magnitude at money scale, requiring a caller to supply more precision than a double
holds. Not, in delivery's judgement, an emergency — but it is a governance control
admitting a value its policy forbids, and that is core's call to size, not delivery's.
**W3 closes it** (`parse_float=Decimal` at ingress, `NumericBound` to `Decimal`).

**One implementation note W3 must not miss:** `bounds.py:36` type-checks
`isinstance(value, int | float)`, so a `Decimal` param is currently rejected outright
as "must be numeric". Landing `parse_float=Decimal` without changing that line would
deny every numeric parameter — a fix that half-lands is worse than the defect.

**The question for core:** disclosure now against `≤0.3.6`, and/or a `0.3.7`? Both
S2 and S3 are named in `0.4.0`'s CHANGELOG per R016 regardless.

## 3. Forward 004 — gate audit: clean, with two honest notes

**The hazard is live on this host**: `python3 -c "print(...)"` prints "Python was not
found" and **exits 0**.

**No gate of delivery's has ever been invoked as `python3`.** CI uses
`actions/setup-python` then bare `pytest`/`ruff`/`mypy`; every local gate ran through
an explicit `.venv/Scripts/*.exe` path; every subprocess in tests and scripts uses
`sys.executable`, never a name. A guard test now fails if any command we publish
spells it. Two notes rather than a bare "clean":

- **One historical claim is unverifiable.** `ESCALATION-2026-08-20-004` (previous
  session) records `python3 validate.py --selftest  # 20/20 PASS`. On this host that
  command attests nothing. Delivery cannot determine whether it ran. It is moot
  rather than wrong: the artifact was independently re-verified this session with a
  real interpreter and visible output, and `tests/reference/` now runs it in CI via
  `sys.executable`. Recorded rather than quietly dropped, because "probably fine" is
  the reasoning this rule exists to replace.
- **Delivery had drifted into exit-code-only gate checks.** Several recent runs used
  `ruff check . >/dev/null 2>&1; echo $?`. The binaries are real, so those gates did
  run and the claims hold — but the pattern is exactly what Forward 004 §2 forbids,
  and it would have hidden this class had the interpreter been the aliased one. Gates
  are now checked against their output contracts (`All checks passed!`, `Success: no
  issues found in N source files`, a test count), not process status.
