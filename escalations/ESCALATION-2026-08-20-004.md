## E12 · The Merkle construction has the duplicate-last-node collision (CVE-2012-2459 class)

**Severity: high for `ND-017`. Not yet shipped anywhere, which is why now is the time.**

`merkle_root` duplicates the final node on odd levels:

```python
if len(level) % 2:
    level.append(level[-1])
```

That is the Bitcoin construction, and it has the known consequence that **two different
leaf sets produce the same root**:

```
root([A,B,C])   = 420940ee1c7a73de80cfa2554efb4e6cec7ea745fed73108ccb06886054df8c6
root([A,B,C,C]) = 420940ee1c7a73de80cfa2554efb4e6cec7ea745fed73108ccb06886054df8c6
                  ^^ identical
```

An anchor is supposed to be an unambiguous commitment to *exactly* the set of receipts
it covers. This one is not: a published root admits more than one preimage set, so an
operator can equivocate about what a given anchor attested. Sorting and de-duplicating
the id list narrows it in practice — `anchor()` does sort — but the property should
hold **by construction**, not by an invariant maintained one layer up in a caller that
`canonical.py` does not control.

**Fix:** RFC 6962 §2.1. Do not duplicate; split at the largest power of two below `n`
and promote the unpaired node. Delivery can supply the patch if core wants it in the
artifact rather than only in onedoor.

## E13 · No leaf/internal-node domain separation — internal nodes are forgeable as leaves

**Severity: high, and it is the one that actually breaks third-party verification.**

Leaves and internal nodes are hashed in the same domain — no `0x00` / `0x01` prefix:

```
root([A,B])                       = 63956f0ce48edc48a0d528cb0b5d58e4d625afb14d63ca1bb9950eb657d61f40
root([ <that same value as a leaf> ]) = 63956f0ce48edc48a0d528cb0b5d58e4d625afb14d63ca1bb9950eb657d61f40
                                        ^^ an internal node passes as a leaf
```

This is the classic second-preimage attack the RFC 6962 prefixes exist to prevent. Its
consequence lands precisely on the claim roadmap §3.2 makes for P3 — that onedoor's
receipts *pass* Veto because "anyone can recompute the decision and check the archive's
integrity independently." Independent checking means **inclusion proofs**, and an
inclusion proof over an undifferentiated tree can be forged: a path can be presented
that proves an internal node is a leaf.

**Related gap:** there is no inclusion-proof function in the artifact at all. `anchor()`
produces a root; nothing produces or verifies a Merkle path. A root alone lets a holder
of the *whole* set recompute it — it does not let a third party verify that *their one
receipt* is in it, which is the entire value proposition. `ND-017` needs
`inclusion_proof(leaf, leaves) -> path` and `verify_inclusion(leaf, path, root)`, and
the domain-separation fix has to land **before** those are frozen, because it changes
every digest in the tree.

**Fix:** RFC 6962 §2.1 — `leaf_hash = SHA256(0x00 || entry)`,
`node_hash = SHA256(0x01 || left || right)`. Together with E12 this is one small patch
to one function.

## E14 · The canonical form is Unicode-version dependent, and nothing records which version

**Severity: medium. Latent, and it is the kind that surfaces years later on an archive
nobody can re-verify.**

`canonical.py` normalises with `unicodedata.normalize("NFC", …)` and `instruments.py`
folds with `str.casefold()`. Both are defined against the Unicode Character Database
**bundled with the running Python**, and that version moves: this check ran on UCD
14.0.0; a verifier on a newer Python carries a different one.

For text containing codepoints assigned or recomposed in a later UCD revision, NFC and
casefold can differ — so two honest verifiers on different runtimes can compute
different `e_digest` / `v_digest` values from identical inputs and disagree about
whether a manifest verifies. **The manifest records no Unicode version**, so there is
no way to tell that this is what happened.

This bears directly on §evidence's re-derivability floor. A verdict that is re-derivable
only on the runtime that sealed it is not re-derivable in the sense the standard means.

**Delivery suggests** recording `unicode_version` in the manifest and folding it into
the instrument identity — an instrument is only pure relative to a fixed UCD. Two-line
change now; unfixable later, because existing receipts are frozen. **Core's call**, as
it is a §evidence/§messages question rather than an implementation one.

## Minor findings (delivery will handle; no ruling needed)

1. **`validate.py` never enforces `manifest.schema.json`.** A sealed manifest carrying
   an extra field is self-consistent and `verify()` returns VERIFIED, while
   `jsonschema` rejects it (`additionalProperties: false`). Integrity is not at risk —
   the extra field changes `manifest_id` — but the schema is currently decorative.
   Wire the schema check into `verify()`.
2. **`verify()` does not check the `schema` field.** A manifest declaring a different
   schema version still verifies.
3. **Evidence-ref path traversal.** `evidence_dir / m["evidence"]["ref"]` has no
   containment check; `ref: "../canonical.py"` escapes the evidence directory. Reference
   implementations get copied — worth a `resolve()`-and-contain check.
4. **`int` and canonical-decimal-string are both admissible for a quantity.**
   `digest_obj({"limit": 250})` and `digest_obj({"limit": "250"})` differ. Rule 4 forbids
   floats but permits ints, so semantic-equality-⇒-byte-equality holds only if each
   schema pins the type. onedoor's `budget` object does pin it (decimal strings), so this
   is a caution for preimage definitions at `ND-017`, not a defect today.

## What this settles for E10 — by demonstration rather than by ruling

The artifact answers my E10 sub-question 1 in the affirmative, which is worth making
explicit before delivery builds on it. `canonical.py` uses **two different disciplines
on purpose**:

- **Archived evidence** is hashed **verbatim** — `digest_file()`, byte-for-byte, with
  the docstring "Evidence files are archived verbatim and content-addressed as-is."
- **Generated structures** (verdict, instrument spec, trust set, the manifest itself)
  are **canonicalised** before hashing.

That is exactly the hybrid delivery was groping toward for `params_json`: **record and
digest what was received; canonicalise only what onedoor generates.** It preserves
forensic fidelity and still gives cross-implementation determinism where onedoor
controls the bytes.

**Confirm this generalises**, and E10 resolves without further design: `params_json`
and `payload_json` are received data, archived and digested verbatim, with their digest
in the chain; `budget_json` and the rest of the row are generated and canonicalised.
The remaining sub-question stands — whether a JSON number arriving in params should be
parsed with `parse_float=Decimal` so `cost_param` never resolves a cost through an IEEE
double. That one is a correctness matter independent of hashing, and delivery would
like it ruled either way.
