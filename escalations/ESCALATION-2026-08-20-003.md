## E10 · `params_json` is inside the preimage and outside the canonicalisation

**Gates `ND-001` (again). Delivery cannot write a chained row without this.**

E8.6 rules: *"One form everywhere: wire, stored `budget_json`, and hash preimage…
From `0.4.0` the canonical form is the wire form."* Sound as a principle. But the
ruling reasons about fields **onedoor generates**. The audit row also carries two
fields onedoor **receives**, and they are in the preimage:

```python
# guardrail/audit.py:64
json.dumps(request.params, default=str),
# guardrail/audit.py:72
None if payload is None else json.dumps(payload, default=str),
```

That call is non-canonical in four separate ways:

| Aspect | Today | Consequence for a hash preimage |
|---|---|---|
| **Key order** | absent `sort_keys` ⇒ Python dict insertion order ⇒ **the order the PEP's JSON happened to arrive in** | Two byte-identical-in-meaning requests with different key order produce different `row_hash`. Directly contradicts E3's "JSON key ordering = sorted". |
| **Separators** | default `", "` / `": "` (with spaces) | Serialiser-specific. Any non-Python verifier disagrees on byte one. |
| **Numbers** | Python `repr` semantics — `json.dumps(250.00)` → `250.0`; `json.dumps(0.1+0.2)` → `0.30000000000000004` | **Directly violates E8.1–2.** IEEE doubles are exactly the "never float" case §messages forbids, arriving through the one door that doesn't check. |
| **`default=str`** | non-JSON types stringified via Python's `str()` | Lossy and Python-specific. A `Decimal` param becomes whatever `str()` gives — the trap you flagged, in the params path rather than the budget path. |

**The tension is real, not cosmetic.** E8.6 forbids the obvious fix. If delivery
canonicalises params at ingress and stores that, then stored bytes ≠ received
bytes, and the evidence row records a *normalised* version of what the PEP sent
rather than what it sent. If delivery hashes the stored bytes as-is, the chain
covers non-canonical bytes and two conformant PDPs handed the same request produce
different chains — which defeats the point of content-addressing at `ND-017`.

**Ruling requested — three sub-questions:**

1. **Does the evidence record what was *received*, or a canonical normalisation of
   it?** This is a §evidence question about fidelity, and it is genuinely
   two-sided: byte-fidelity is the better forensic story, canonical-normalisation
   is the only one that makes cross-implementation verification work. Delivery
   leans **canonicalise at ingress and record the canonical form**, with the
   received bytes' digest recorded alongside so fidelity is still attestable — but
   that adds a column and is a spec decision.
2. **What is the canonical JSON form for arbitrary PEP-supplied params?** Sorted
   keys, `(",", ":")` separators, UTF-8, NFC, and — the hard one — **what happens
   to a JSON number.** JSON has one numeric type and it is not decimal. Delivery
   suggests: numbers in params are canonicalised by the E8 decimal rule, parsed
   with `parse_float=Decimal` so nothing ever becomes an IEEE double. That makes
   `250.00` and `250` hash identically, consistent with E8's semantic-equality
   goal. **Confirm, because it changes what `cost_param` resolves against.**
3. **Does this apply to `payload_json` too?** It is connector-supplied result data
   on the `exec_result` row, so the same reasoning applies with the direction
   reversed.

**Note on scope:** whatever the answer, it lands in the `0.4.0` migration, not
`ND-001` — the row format has to be right before anything hashes it. This is the
same "rename before you chain" logic as C1, one level down.

## E11 · "Safe by construction" is not true of onedoor's PEPs — there is no obligation machinery

**Not a spec defect. A gap in the reference implementation that E9's reasoning
assumes closed.**

E9's elegance rests on: *"old PEPs are safe by construction, because a PEP that has
never heard of `idempotency_key` already fails closed on it (§obligations)."*

That is correct **about the standard** and false **about onedoor**. Verified at
`3dfe3cd` — every occurrence of the word "obligation" in the package:

```
guardrail/decision.py:12   ":class:`PermittedIntent` — an obligation for the caller to enforce."
guardrail/decision.py:57   "A permitted action whose execution is now the caller's obligation."
service/app.py:5           "POST /v1/decide  submit an ActionRequest -> decision (+ obligation)"
service/app.py:20          "Obligations across the wire: a permitted decision returns an ..."
service/notify.py:10       "notification is an obligation of the operator, not of the pipeline."
```

**All five are prose using the word colloquially.** There is no obligation type, no
obligation field on the permit, no discharge evidence, no `not_attempted` outcome,
and no unknown-obligation check anywhere. The audit's `decision` column admits
exactly `executed | dry_run | proposed | denied | failed`.

**The safety consequence.** onedoor's packaged PEPs — the MCP stdio proxy and the
LangChain middleware — do not fail closed on an unknown obligation. They have no
obligation code path at all, so an obligation attached to a permit would be
**silently ignored and the action executed anyway.** For `idempotency_key` the
blast radius is a duplicate effect. For `isolate` (A5) it would be an action that
the policy required to be contained running uncontained, with the audit recording
a clean success. The fail-closed guarantee §obligations relies on is a property of
*conformant* PEPs, and onedoor's are not yet conformant on this axis — which the
draft's honesty discipline says should be visible rather than assumed.

**Three consequences for the backlog, all delivery's to absorb:**

1. **`ND-008` re-sizes M → L, and gains a dependency.** It is no longer "derive a
   key and thread it through adapters." It now needs obligation emission on the
   permit, PEP-side unknown-obligation fail-closed, discharge evidence on the
   report, and a `not_attempted` outcome.
2. **New foundational ticket `ND-038` — obligation machinery.** Delivery is adding
   it: the obligation envelope on `PermittedIntent`, the registry check, PEP-side
   fail-closed in both packaged PEPs, discharge evidence in the report, and
   `not_attempted`. **`ND-008` (A3), `ND-030` (A5 `isolate`), and `ND-037` (A9a)
   all depend on it.** It is the shared substrate none of the three can be built
   without, and it was invisible in the roadmap because the roadmap treats them as
   three unrelated items.
3. **`ND-037` was mis-marked.** Core's B3 called registry hygiene
   "conformant-checkable" and delivery recorded "emit only registered types,
   enforce unknown-obligation-fail-closed" as a small ticket. Neither duty can be
   *enforced* against machinery that doesn't exist. Re-marked as blocked on
   `ND-038`.

### The sequencing question this raises — and it is time-sensitive

`not_attempted` is a **new value in a wire-observable enum**, and obligation
discharge evidence is a **new field on the report**. Both are exactly the kind of
change E1.3 rules on. Response 001 stated the `0.4.0` vocabulary change is complete
in one increment: caps rename + `sender_mismatch`. **E9's own ruling breaks that
promise** — it introduces at least one more wire-observable vocabulary addition,
currently scheduled for `0.5.0`.

So `0.4.0` is not the last breaking increment unless something changes.

**Delivery's recommendation, needing core's assent because it is wire-observable:**
**reserve the obligation surface in `0.4.0`** — the `obligations` field on the
permit, `not_attempted` in the outcome enum, the discharge-evidence field on the
report — all present, all unused until `ND-038`/`ND-008` fill them. Exactly the
present-but-empty discipline E3 already blessed for the receipt envelope, applied
to the same problem one layer up. Ship one breaking increment, not two.

The alternative is honest and also fine: accept that `0.5.0` is a second breaking
release and say so plainly in the changelog. Delivery would rather reserve.
