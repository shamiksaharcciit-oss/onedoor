# `ND-052` / **S5** — the finance/payments template pack · decomposition

**Epic:** `ND-052`, the Policy Studio. Pre-launch, demo-grade (R036).
**Ticket:** S5, fifth in the normative build order, on the coverage map S4 just proved.
**Baseline:** `abaef9d`; four gates green via `python -m scripts.gate --all`, 771 passed.
**GO:** R050 §5.

---

## 1. The fence carried in, and what it decides

R050 §5, unasked and correct:

> A template pack ships **policy**, and policy is now bound by Q3's law — **no template
> may name an effect it does not also declare.** The pack is the first artifact that
> would have shipped the defect at scale, so its own tests should assert the law rather
> than assume it.

That fence decides more than it looks. A pack is **not** documentation that happens to
contain YAML; it is policy this project authored and a deployer will trust. Every law
binding policy binds it, and the pack is the first place those laws meet *scale* —
one defect in one template becomes one defect in every deployment that adopts it.

Also carried in, from the constitution: **principle 3** — *adjustable parameters are the
review surface and defaults are fail-closed* — and **principle 4** — *non-coverage is
stated, never silent*, which the pack owes about itself.

## 2. Finding one: a pack outside the package does not ship at all

Measured, not assumed. `pyproject.toml` has `include = ["onedoor*"]`, and the `0.5.0`
wheel contains **no** `config/policies.yaml`:

```
migrations in wheel: 18 ...      onedoor/store/migrations/*.sql
vendored oneview spec:           onedoor/viewer/_vendor/ONEVIEW_DESIGN_SPEC.md
config/policies.yaml:            ABSENT
```

The repo's existing policy file is a **development seed**, not a shipped artifact — a
distinction nothing in the tree currently states. So the pack lives in
`onedoor/templates/`, beside the migrations and the vendored spec, and **a test asserts
it is in the built wheel**. That is the `0.3.0` class — a wheel that shipped no migrations
and failed on first query — and the ND-051 lesson that *a repo directory does not travel
in a wheel*.

## 3. Finding two: the law the pack must assert is wider than the effect half

R050's fence names the effect rule, and the effect rule is one **case** of the law
`CONFORMANCE.md` now records as binding on all policy:

> **A protection that depends on a second, optional declaration is not a protection — it
> is a default.**

Its other recorded case is `ND-040`/U4: a policy with an `opaque` block and an effect
whose `min_tier` is `null` let an opaque host auto-execute. A payments pack is exactly
where that shape would appear — an egress rule with an opaque-host block is the *natural*
thing to write. **So the pack's tests assert the law family, not the single case that
prompted the fence.**

And they assert it **through the engine's own checkers** — `coverage.build`'s
`declared_inert` rows and `validate_policy` — never a second implementation written for
the pack. Fence post two: a checker with its own idea of what makes a policy unsafe will
disagree with the engine, in the direction that lets a bad template through.

## 4. Finding three: a placeholder is a second declaration

The obvious template design is a file with blanks — `eur_day: {{daily_cap}}` — that a
deployer fills in. **That design is forbidden by the very law this ticket is fenced by**,
and it took writing the fence down to see it:

- A template whose safety depends on the deployer supplying a value is *a protection that
  depends on a second, optional declaration.*
- Worse, a blank is not a `Policy`. `validate_policy` cannot check it, `coverage.build`
  cannot map it, and the pack's own tests would be asserting the law against something
  that is not yet policy — the check passing before the artifact exists.

So templates are **concrete policies with fail-closed defaults**. *Adjustable* means the
deployer edits a real value that was already safe, which is principle 3 read strictly
rather than loosely: the review surface is a number you can see and change, not a hole
you must remember to fill.

## 5. Finding four: a pack is an instrument, and an instrument needs an identity

S6 records *model + prompt + **template pack*** as the instrument in the derivation
receipt. **An instrument without an identity cannot be recorded**, so the pack needs one
before S6 needs it — which is now, not later.

The Oneview spec already shows the shape: vendored into the package, digest-pinned, with
the digest generated by tooling and never typed (X-11). What that digest is *of* is §8's
second question.

## 6. Finding five: the pack must be exercised, not merely validated

A template that parses is not a template that does what it says. The pack's tests should
**decide real requests against each template** and assert the verdicts — a €50 refund
permitted, a €5,000 one sent to a human, an egress to an opaque host refused — so the
tests document what each template *does* rather than that it loads.

*Run, don't read*, applied to an artifact whose whole purpose is that someone else will
trust it without reading it.

## 8. The questions this decomposition surfaces

**1. How much does the pack claim?** *"A finance/payments template pack"* implies domain
authority, and **delivery has none** — this project is a policy engine, not a payments
compliance authority. A deployer who reads "payments pack" as "these are the controls
payments needs" has been overclaimed to, and that is the failure mode this programme
exists to make impossible. Delivery proposes the pack describe itself as **a worked
example that demonstrates the vocabulary**, explicitly *not* a compliance artifact, with
its own gaps stated on its face. If the launch wants a stronger claim, that is core's
call and it needs someone who can stand behind it — delivery cannot, and would rather say
so now than write a README that implies otherwise.

**2. What is the pack's digest *of* — the files, or the policy set they load to?** Two
candidates answering **different questions**, which is the reason this is a question at
all rather than a preference:

  - a **file digest** pins *what shipped* (the `SPEC_DIGEST` pattern) and changes when a
    comment changes;
  - a **canonical-policy-set digest** pins *what it means* (the `policy_digest` shape) and
    is stable across re-spellings.

  *A digest answers exactly one question* (X-11), so delivery's lean is **both, named for
  their different jobs** — file digest for "is this the pack we shipped", meaning digest
  for what a receipt cites. Delivery flags it rather than deciding because two digests on
  one artifact is also exactly the shape of *two fields that must agree* (X-14), and
  delivery is not certain which reading core wants to win.

**3. Does adopting the pack go through the ratification ceremony?** A deployer loading the
pack is **changing the rules their engine enforces** — which is the act S2 built a
ceremony and a receipt for. Delivery leans **yes**: loading a pack produces a
`ratifications` row whose `candidate_digest` is the pack's, so *"why does this policy
allow X?"* is answerable years later by provenance rather than memory — principle 5,
reached without new machinery. The alternative is a plain `load_file` upsert, which is
what exists today and which would make the pack the one policy change in the product that
leaves no receipt.

T1, T2, T3 and T5 are unblocked. T4 waits on Q2; T6 waits on Q1.

## 9. One finding carried forward from S4, needing a ruling

**`UNOBSERVED` has the defect R050 §4 just ruled on, one layer up.** The ruling renamed
`exercised_effects` because *the word claimed history and the computation is a
projection*. The state name `unobserved` makes the same claim: it says an observation was
made and came back empty, when **effects are never observed at all** — the ledger does not
record them. What the state actually means is *no observed action type would reach this
effect under this policy set*.

Delivery has **not** renamed it, because core named that state in R049 §4 while ruling it
into existence, and delivery does not rewrite a ruling's vocabulary on its own authority.
Proposed: `UNREACHED`, or core's better word. Raising it rather than acting on it, and
raising it rather than leaving it, because naming-honesty is settled programme law and
this is the same defect the law was just applied to.
